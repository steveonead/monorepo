# ito-best-practices

## 概覽

引導使用者為指定技術建立結構化 best practices skill，產出可直接使用的 `SKILL.md` 與 `references/` 規則目錄。也可審查現有規則集的語言與結構品質。

## 使用時機

- 使用者說「建立 X best practices skill」、「幫我建 X 的最佳實踐」或呼叫 `/ito-best-practices`
- 使用者說「審查 X best practices」或「review X 的規則」，想改善現有規則的文字品質
- 使用者有技術名稱、文件連結或粗略規則清單，想整理成結構化 best practices
- 需要為現有技術建立可供 agent 引用的規則集

**不應使用的情況：** 撰寫 PRD、建立非 best practices 性質的 skill。

## 核心流程（建立 / 更新）

### 步驟 1：開場與素材收集

依序詢問，一回合一題：

1. 第一題：要為哪個技術建立 best practices？
2. 取得技術名稱後，第二題：是否有素材要帶入？（文件連結、現有規則清單，可選）
3. 第三題：範例程式碼有無需要遵守的慣例？（如 import 路徑格式、命名規則、框架特定寫法，可選）

記錄回應做為候選規則的基底。

### 步驟 2：衝突檢查

檢查 `.claude/skills/<技術名稱>-best-practices/` 是否已存在：
- 若不存在，直接進入步驟 3
- 若已存在，詢問使用者：A）更新既有規則 或 B）從頭建立（內容全部重寫）
  - 選 A：讀取現有 `SKILL.md` 與所有 `references/*.md`，以現有規則做為步驟 3 的初版候選規則清單
  - 選 B：直接進入步驟 3，從零產出候選規則清單

### 步驟 3：候選規則產出

**優先檢查 ARGUMENTS**：若 ARGUMENTS 中包含搜尋意圖（如「搜尋」、「查」、「社群」、「參考資料」、「文件」），在產出候選清單前先執行對應查詢，以查詢結果為基底產出規則，不從自身知識直接回答。可用工具同步驟 4 的深挖工具。

根據使用者素材與本身知識，產出初版候選規則清單。

每條格式：
```
<類別前綴>-<規則名稱> — <一句話說明>
```

**規則命名原則**：名稱應具體到「這條規則解決什麼問題」，避免過廣。例如 `hooks-usage` 邊界不清，應具體化為 `hooks-dependency-array` 或 `hooks-avoid-inline-object`。

數量依技術複雜度彈性決定，不設硬性上下限。

### 步驟 4：討論循環

重複以下循環直到收斂：

1. **使用者標記** — 使用者指出要深挖、修改或刪除的規則
2. **深挖** — 對標記規則追問細節、範例、邊界條件。若使用者要求查詢，依需求選擇工具後摘要帶回討論，不主動搜尋：
   - **Exa**：搜尋技術 KOL 部落格與實戰文章
   - **Context7**：查閱官方文件，確認新版 API 的正確用法
   - **DeepWiki**：查閱 GitHub 專案文件與架構說明

3. **規則更新** — 納入討論結果，更新規則清單
4. **分類檢查** — 分類以功能職責切分，不以技術細節切分。單一分類下少於 2 條規則時，考慮合併或重新歸類。
5. **收斂判斷** — 當覆蓋足夠、無明顯空白時，主動提議：「規則覆蓋看起來已足夠（目前 N 條，涵蓋 [分類摘要]）。要進入草稿確認，還是繼續討論？」

### 步驟 5：草稿確認

在對話中展示摘要：
- 規則總數與分類列表（每個分類的規則數）
- 本輪新增、修改、刪除的規則（若為迭代）

使用者確認後進入步驟 6（驗證），否則返回步驟 4。

### 步驟 6：規則驗證

以分類為單位，並行啟動 sub-agent 驗證規則正確性。驗證範圍：

- **API 規則**：用 Context7 確認 API 用法與最新版文件一致
- **社群/官方 best practice**：用 Exa 或 Context7 查詢社群共識或官方建議
- **純風格/命名規則**：跳過驗證

每條規則輸出 ✅（正確）、⚠️（有疑慮或社群有爭議）、❌（與文件或社群共識不符）。

驗證完成後展示報告，詢問使用者：
- 「修正 ❌/⚠️ 規則後重跑步驟 6 驗證」
- 「知道有問題，仍繼續寫檔」

### 步驟 7：寫檔案

1. 讀取 `assets/writing-guidelines.md`，作為撰寫每條規則的語言與結構依據
2. 讀取 `assets/output-skill-template.md`，填入技術名稱、分類、規則清單，寫出 `.claude/skills/<技術名稱>-best-practices/SKILL.md`
3. 以分類為單位，並行啟動 sub-agent，讀取 `assets/rule-template.md`，依每條規則填入內容，寫出對應的 `.claude/skills/<技術名稱>-best-practices/references/<類別>-<名稱>.md`

## 審查模式

使用者說「審查 X best practices」或「review X 的規則」時觸發。

### 步驟 1：確認目標

確認技術名稱，檢查 `.claude/skills/<技術名稱>-best-practices/references/` 是否存在。若目錄不存在或為空，告知使用者該技術尚未建立規則集，中止流程。

### 步驟 2：讀取審查依據

讀取 `assets/writing-guidelines.md`，作為審查基準。若檔案不存在，中止並告知使用者。

### 步驟 3：逐檔審查

讀取所有 `references/*.md`，依照寫作指引找出問題，分兩階段：

**逐檔審查**，分類為：
- **語言問題**：翻譯腔、禁用套語、口語化字眼、英文直翻語序、技術措辭直譯
- **標點問題**：程式碼區塊外出現半形分號（`;`）
- **結構問題**：缺 Bad/Good 範例、多餘 section、應條列卻以段落呈現

**全局掃描**：統計每個形容詞或固定詞組在全部規則檔案中的出現次數，超過 2 次的標記為「跨檔案重複」。

### 步驟 4：展示報告

在對話中展示審查報告，以規則檔案為單位列出問題：

```
📄 <規則檔案名>
  語言：[具體問題]
  結構：[具體問題]
```

報告末尾列出問題總數，詢問：「確認後統一套用所有修改，要繼續嗎？」

### 步驟 5：Apply

使用者確認後，一次修改所有有問題的規則檔案，回報修改了哪些檔案。

## 常見合理化藉口

| 合理化藉口 | 實際情況 |
|-----------|---------|
| 「使用者沒有標記問題，可以直接寫檔了」 | 需主動判斷覆蓋是否足夠，不等使用者先宣告完成 |
| 「只有技術名稱，沒辦法產候選清單」 | 技術名稱本身就是足夠的基底，本身知識可補足初版清單 |
| 「規則夠多了，不用問了」 | 數量不等於覆蓋，需確認分類是否完整、有無明顯空白 |
| 「ARGUMENTS 沒說要搜尋，所以直接產清單」 | ARGUMENTS 是使用者在呼叫時給的指示，同樣算使用者要求，必須在步驟 3 執行 |
| 「主動搜尋比較快」 | 步驟 4 討論中不主動搜尋，但 ARGUMENTS 明確要求的除外 |
| 「審查完使用者確認了，直接修」 | 需先展示報告讓使用者確認，才修改檔案 |
| 「草稿確認後直接寫檔就好」 | 驗證步驟永遠在寫檔前執行，不可跳過 |
| 「分類多，自己寫比較快」 | 每個分類必須啟動獨立 sub-agent，不用 sub-agent 會塞爆 context |

## 警訊

- 未詢問素材就直接產候選清單
- ARGUMENTS 含搜尋意圖卻未在步驟 3 執行查詢，直接從自身知識產清單
- 步驟 4 討論中使用者未要求卻主動觸發 Exa、Context7 或 DeepWiki
- 草稿摘要未列分類，使用者無法評估覆蓋完整性
- 規則檔案命名未使用類別前綴
- 審查報告未以規則檔案為單位列出問題
- 未展示審查報告就直接修改檔案
- 跳過步驟 6（驗證）直接進入步驟 7（寫檔）
- 步驟 7 未以分類分批並行，用單一流程寫全部規則

## 驗證

建立 / 更新模式：
- [ ] `.claude/skills/<技術名稱>-best-practices/SKILL.md` 已寫出
- [ ] `.claude/skills/<技術名稱>-best-practices/references/` 下每條規則有對應 `.md` 檔
- [ ] 使用者確認草稿摘要後才觸發驗證
- [ ] 驗證報告展示後使用者確認才觸發寫檔

審查模式：
- [ ] 審查報告展示後使用者確認才 apply
- [ ] 修改完成後列出所有被修改的檔案

## 延伸參考

- `assets/writing-guidelines.md`：規則寫作指引，包含格式規範、語言風格與 AI 寫作常見問題清單，建立 / 更新 / 審查模式均須讀取
- `assets/output-skill-template.md`：產出 skill 的 SKILL.md 模板，步驟 7 時讀取
- `assets/rule-template.md`：個別 rule 檔案模板，步驟 7 時讀取
