# ADR 格式

ADR 放在 `docs/adr/` 目錄下，依序編號：`0001-slug.md`、`0002-slug.md`，以此類推。

`docs/adr/` 目錄採懶建立，等到第一份 ADR 真正需要時再建。

## 模板

```md
# {決策的簡短標題}

{1-3 句話：背景是什麼、我們做了什麼決定、以及原因。}
```

就這樣。一份 ADR 可以只有一段話。重點是記錄「做了什麼決定」與「為什麼」，而不是把每個區塊都填滿。

## 選用區塊

只有在真正有幫助時才加。大多數 ADR 不需要這些。

- **狀態** frontmatter（`提議中 | 已接受 | 已棄用 | 被 ADR-NNNN 取代`），決策被重新討論時有用
- **評估的方案**，只有當被否決的方案值得留存時才寫
- **影響**，只有當下游影響不夠明顯、需要特別說明時才寫

## 編號

掃描 `docs/adr/` 中現有的最高編號，加一。

## 何時建立 ADR

必須同時符合以下三個條件：

1. **難以逆轉**，之後改變主意的代價是真實且顯著的
2. **沒有背景就會令人困惑**，未來的人看到這段程式碼，會忍不住問「為什麼要這樣做？」
3. **真正做了取捨**，有具體的備選方案，並因為特定原因選了其中一個

如果決策容易逆轉，不用寫，到時候直接改就好。如果決策不會讓人困惑，沒人會追問為什麼。如果根本沒有其他選擇，就沒什麼好記的。

### 哪些決策適合寫成 ADR

- **整體架構走向。** 「我們採用 monorepo。」「寫入端用 event sourcing，讀取端查 Postgres。」
- **context 之間的溝通方式。** 「Ordering 與 Billing 透過 domain event 溝通，而非同步 HTTP。」
- **難以替換的技術選型。** 資料庫、訊息佇列、auth provider、部署環境。不是每個套件都要寫，要換就要大動工的才算。
- **職責邊界與範圍。** 「Customer 資料由 Customer context 擁有，其他 context 只能透過 ID 參照。」明確的「不做什麼」和「要做什麼」同樣重要。
- **刻意不走常規的決策。** 「我們用手寫 SQL 而非 ORM，因為 X。」任何合理的人會預設做相反事情的地方，都值得記錄，避免下一個工程師「修掉」一個其實是刻意為之的決策。
- **程式碼看不到的限制。** 「因為法規要求，不能使用 AWS。」「因為合作方 API 合約，回應時間必須在 200ms 以內。」
- **被否決的方案，且否決原因不明顯。** 如果你評估過 GraphQL 但因為細微原因選了 REST，記錄下來，否則六個月後有人又會提議 GraphQL。
