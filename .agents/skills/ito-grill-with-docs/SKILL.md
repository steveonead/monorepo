# ito-grill-with-docs

## 概覽

無情追問計畫的每個決策分支，壓力測試所有假設，同時即時維護領域術語表（CONTEXT.md）與架構決策紀錄（ADR）。確保術語與程式碼對齊，決策有據可查。

## 使用時機

- 使用者說「我想討論⋯」或「幫我釐清⋯」，討論關於 codebase 設計或實作，且需要留下文件
- 需要壓力測試設計，同時建立或維護領域術語表
- Project 有 CONTEXT.md 或 ADR，討論時需要對齊既有術語
- 方向尚未確立，需要探索可能性、挑戰假設再收斂，並將結果記錄成文件

**不應使用的情況：** 只需要討論、不需要文件的情境、需要直接實作的任務、方向已確立需要整理成規格。

## 核心流程

### 步驟 0：讀取既有文件

開始追問前，先探索 project 的文件結構：

- 若存在 `CONTEXT-MAP.md`，讀取後找出所有 context 及其 `CONTEXT.md` 位置
- 若存在 `CONTEXT.md`（root 或 context 子目錄），讀取術語表
- 若存在 `docs/adr/`，掃描既有 ADR，取得最大編號
- 三者皆不存在時，記錄「文件尚未建立，術語確認時懶建立」

讀取完畢後一句話複述現狀，再進入步驟 1。

### 步驟 1：一回合問一題，不斷追問

沿決策樹分支深挖，先處理有依賴關係的決策。**預設假設計畫存在脆弱點**，主動找出模糊假設，而非被動收集資訊。

**核心守則：**
1. 一回合只問一題，追問留至下一回合
2. 每個回答都是下一個問題的起點，找出隱含假設或潛在弱點再繼續，不因回答聽起來合理就放過
3. 前一決策解鎖新子問題時，先一句話說明依賴關係，再提問
4. 技術問題優先探索 codebase，取得結果後一句話複述並請使用者確認
5. 以簡潔且通順的文字提問，講重點，不堆砌專有名詞或冗長論述

**問題類型：**
- **決策型**（使用者需選方向）：說明情境、列出選項、**附上推薦與理由**
- **現況確認型**（了解既有狀態）：說明原因、列出可能情況，不附推薦
- **開放型**（本質發散的背景問題）：說明為何需要開放回答，直接問，**附上預期或假設**

若能列出 2–4 個互斥選項，優先用決策型或現況確認型。只有問題本質發散時才用開放型。取得開放回答後，立即以決策型或現況確認型往下深挖。

### 文件管理（追問過程中同步執行）

#### 術語對齊

使用者用與 `CONTEXT.md` 衝突的術語時，立即指出：

> 「你的術語表把『cancellation』定義為 X，但你現在似乎是指 Y，哪個才是？」

#### 模糊語言精確化

使用者用模糊或過載術語時，提出精確的標準術語：

> 「你說的『account』，是指 Customer 還是 User？這兩個是不同的概念。」

#### 具體情境壓力測試

討論領域關係時，主動構造邊界情境，迫使使用者對概念邊界給出精確答案。

#### 主動交叉驗證

使用者陳述某個機制的運作方式時，主動去 codebase 確認。發現矛盾立即指出：

> 「你的 code 裡取消的是整筆 Order，但你剛說支援部分取消，哪個才是正確的？」

#### 即時更新 CONTEXT.md

術語確認當下立即更新 `CONTEXT.md`，不等收斂。若 `CONTEXT.md` 尚不存在，第一個術語確認時建立。`CONTEXT.md` 只放術語定義，不放實作細節或決策紀錄。格式參考 [CONTEXT-FORMAT.md](./references/CONTEXT-FORMAT.md)。

#### 即時寫入 ADR

下列三條件全部成立時才提議寫 ADR：

1. **難以逆轉**：事後改變心意的成本有意義
2. **沒有背景看不懂**：未來的讀者會疑惑「為什麼這樣做？」
3. **真正的 trade-off 結果**：有真實的替代方案，選了一個有特定原因

三條件任何一個不成立就略過。格式參考 [ADR-FORMAT.md](./references/ADR-FORMAT.md)。

### 步驟 2：收斂判斷

**所有分支都被覆蓋、所有假設都被挑戰過**後，才主動宣告收斂。判斷標準由 agent 負責，不是使用者說可以就可以。宣告收斂時列出所有未解問題：

> 所有分支已追問完畢，以下問題答案尚未確定：
> - [未解問題 1]
>
> 要繼續討論還是收斂？

使用者說「結束」或「可以了」時，仍依本步驟列出未解問題後再收斂。使用者確認收斂，進入步驟 3。使用者選擇繼續討論，返回步驟 1。

### 步驟 3：收斂後摘要

在對話中條列以下內容：

**本次達成共識的決策：**
- [決策清單]

**未解問題：**（若無列「無」）

**文件更新：**
- CONTEXT.md：新增術語 [term1], [term2], ...（若無變動列「無」）
- ADR：建立 [0001-slug.md], ...（若無建立列「無」）

若需要交接到下一個 session：

> 若要將本次討論帶到下一個 session，跑 `/ito-handoff`。

## 常見合理化藉口

| 合理化藉口 | 實際情況 |
|-----------|---------|
| 「使用者說可以了，不用再問」 | 收斂由 agent 主導，確認所有分支都覆蓋再收斂 |
| 「一次問多題比較快」 | 多題並問讓使用者遺漏分支，破壞決策樹完整性 |
| 「計畫看起來很合理，不需要再釐清」 | 順暢不代表無弱點，模糊假設要主動追問 |
| 「術語等收斂後再統一更新」 | Inline 更新才能保留術語確認當下的脈絡，事後補寫容易遺漏細節 |
| 「這個決策不夠重要，不用寫 ADR」 | ADR 三條件是客觀標準，由難逆轉加沒背景看不懂加真實 trade-off 決定，不由主觀重要性判斷 |

## 警訊

- 一回合出現兩個以上問題
- 決策型問題沒有附推薦與理由
- 開放型問題沒有附預期或假設
- 全程未主動挑戰任何模糊假設
- 使用者陳述機制時未主動查 codebase 驗證
- 術語已確認但未即時更新 CONTEXT.md
- ADR 三條件全中但未提議寫 ADR
